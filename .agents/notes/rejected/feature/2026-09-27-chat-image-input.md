# Agent Note: 聊天图片输入与附件归属

Status: rejected — 首版接受历史图片不可回显，持久附件的成本不再必要；由[本轮临时图片输入](../../implemented/feature/2026-09-27-ephemeral-chat-images.md)替代。

## Problem

聊天输入、发送协议和用户消息历史投影目前只表达文本，用户无法直接提交截图，也无法在刷新或另一客户端中查看同一条请求的图片。图片还需要覆盖尚未创建会话的首页输入，并遵守 Provider 持有原生历史、Racco 不保存逐轮执行账本的边界。

## Proposal

新建和已有会话共用图片输入能力，支持文件选择、粘贴、拖拽、多图及纯图片请求。首版接收静态 PNG、JPEG、WebP，图片先经 HTTP 上传，消息经现有 WebSocket 提交有序的文本与附件引用。上传和历史图片提取共同受容量、字节、像素及解码资源预算约束，限制在像素展开前生效。上传就绪、daemon 受理与 Provider 执行结果分别表达，不静默删图或切换模型。

daemon 持有不可变原图和最小资源元数据，缩略图及可从原生历史提取的图片是可重建缓存；Provider 持有消息、顺序与图片块。Codex 接收受管文件路径，Claude 接收含图片字节的单条结构化用户消息，继续采用每轮 Query。历史关联必须来自原生消息中的图片来源，不能根据会话归属、时间或上传顺序补造消息关系。浏览器按需读取图片字节，用户消息快照只传引用；外部不可用来源保留占位，正常受支持输入丢图不能算验收通过。

临时上传具有有效期，发送占用覆盖异步会话分配并与移除、过期回收互斥。首页先取得原生会话身份，再持久绑定附件并启动首轮；单独上传不创建会话。已绑定资源在取消、失败、移除登记、项目或 Worktree 后保留，避免崩溃或不确定结果导致误删。未确认命令不自动重放，创建请求身份仍覆盖完整有序输入。

原生会话彻底删除后仅清理能证明安全的附件，未知或共享引用保留并报告。清理状态独立于项目及会话登记，失败与重启后仍可继续。另设独立附件管理入口，允许用户明确接受相关历史图片失效后销毁选定资源；不得触碰仍被使用的图片或 Provider 文件。首轮未产生原生记录、工作目录已移除时，资源仍应可见、可管理。数据库破坏性重置须显式处理附件目录，不自动接管旧资源。

输入接口支持不等于历史可恢复。采用前必须验证两家真实图片往返、重启、续聊、分叉引用、编码后限制和 Claude 单消息输入流的结束时序；条件不成立就重审相关设计。只有原生历史能独立恢复图片时，才重新评估只保留可重建缓存的替代方案。协议与资源边界详见[完整设计](../../../../docs/design/chat-image-input.md)。

本提案拟部分扩展[无逐轮执行记录](../../implemented/simplification/2026-09-17-session-state-without-turn-ledger.md)及[原生会话导入](../../implemented/feature/2026-09-18-project-session-import.md)的持久化规模，但保留 Provider 历史归属、只读导入与无消息账本的决定；实施时再更新其存储描述。[完整历史读取](../../implemented/simplification/2026-09-27-full-history-with-websocket-compression.md)继续持有消息快照边界，图片资源及有界派生缓存不构成第二份消息历史。本提案扩展[原生会话删除](../../implemented/feature/2026-09-19-native-session-delete.md)的资源收尾义务，保留[显式磁盘清理](../../implemented/feature/2026-09-21-delete-explicit-disk-cleanup.md)的删除边界；[工具 Output](../../implemented/simplification/2026-09-22-single-tool-output.md)不属本范围。相关记录保留并关联本提案，没有需要拒绝或归档的现有提案。

## Alternatives considered

**直接在 WebSocket 消息和完整历史中嵌入 base64：** 实现较短，但每次订阅都会重复传输图片，扩大 JSON、客户端缓存和内存成本，也难以独立重试上传。

**把图片路径拼入提示词或写入 Worktree：** 依赖 Agent 主动调用读图工具，不能保证图片成为本轮模型输入，还会向工作目录引入与项目文件无关的数据。采用 Provider 原生图片块，并由 daemon 独立保存附件。

**仅暂存图片，轮次结束即删除：** 原生历史可能只保留文件引用，刷新、重新导入或原生续聊可能失效。保留已提交附件直到明确清理，以磁盘占用换取稳定引用。

**清理完全依赖原生会话列表：** 首轮失败、项目或 Worktree 删除后，用户可能无法再从该列表找到清理入口。独立资源管理增加界面与状态成本，但让空间占用及显式销毁始终可达。

## Acceptance criteria

- 新建和已有会话都能向 Codex、Claude 发送图文、多图与纯图片请求；无效附件不会退化为静默发送文本。
- 通过真实 Provider 采用验证后，正常发送的图片在切换客户端、刷新、daemon 重启及重新导入会话后仍可回显，顺序与原生消息一致；外部缺失或不支持来源有明确占位。
- 中断上传、发送失败、断线、并发回收及删除不会造成自动重复提交、跨会话引用泄漏或图片误删；受管原图可读，派生缓存与历史提取不绕过资源上限。
- 项目或原生记录消失后，附件空间与未完成清理仍可查看、处理；主动销毁图片明确表达历史失效后果。

## Risks

持久附件增加磁盘及清理责任，Claude 历史内嵌图片可能造成重复存储和读取内存开销。输入接口已核对，真实历史恢复、分叉与 SDK 结束时序仍是未验证的采用条件。未知引用会限制安全清理，主动销毁则可能使其他原生历史失图，不能将二者混为后台回收。协议与 schema 按项目规则一次更新，旧格式直接拒绝。
