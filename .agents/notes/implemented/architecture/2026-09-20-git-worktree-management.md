# Agent Note: Worktree 管理

Status: implemented

## Problem

Racco 把会话直接挂在项目上，项目的目录就是会话的 `cwd`，一个项目因而只有一个工作目录。同一仓库的两条工作线要并行推进，用户必须在 Racco 之外手工建 Worktree；而 Racco 既看不见这些目录，也无法把会话归到它们名下——右侧文件浏览、原生会话发现、模型目录全部以项目目录为根，语义上不再匹配用户实际的工作单元。

[按项目浏览并显式导入原生会话](../feature/2026-09-18-project-session-import.md)当时把边界定为"项目边界采用规范化目录，不扩展到其他 worktree"；本决策反转该约束，该记录中这一句已按新边界改写。

## Decision

引入 Worktree 作为项目与会话之间的中间层：`Project (1) → (N) Worktree (1) → (N) Session`。会话的 `cwd`、文件浏览、原生会话发现、模型目录都以所属 Worktree 为根，不再以项目目录为根。

**Worktree 列表从 `git worktree list --porcelain` 派生，Racco 不维护自己的 Worktree 注册表。** 仓库里存在的每一个 Worktree 都会出现：Racco 创建的、用户在终端手工创建的、`--detach` 的、以及目录已被删除但元数据尚存的（标为 `prunable`）。列举以 Git 为唯一事实来源，Racco 不隐藏它没创建的东西。Racco 只负责创建与删除，且只在自己的创建位置（默认 `~/.local/share/racco/worktrees`，可由 `racco.config.json` 的 `worktreeRoot` 改到别处）下创建；`worktreeRoot` 只约束创建，不约束列表。

**Worktree 的身份是它的绝对路径。** `git worktree list` 报告的路径是权威值；`.git/worktrees/<admin-name>/` 的目录名是历史产物（`git worktree move` 后路径变了、admin 名不变），不能作身份。Git 记录路径时会做规范化，所以 `worktreeRoot` 在配置加载时即按真实路径解析一次，避免同一目录以两种写法出现。路径也是 `sessions.cwd` 已持有的值，会话与 Worktree 的关联因此不需要新列。

**界面固定显示三层——项目 → Worktree → 会话，不因项目只有一个 Worktree 而省略中间层。** 树形不随数据变化，新建第一个 Worktree 不会让项目重新排布。代价是单 Worktree 项目多出一层嵌套，明确接受。选择 Worktree 是主轴状态，右侧 Dock 与新建对话都跟着它；切换会话时同步选中其 `cwd` 所属的 Worktree，之后的手动选择保持有效，不被当前会话持续覆盖。

**列表只在用户显式请求时刷新，没有任何周期性或事件驱动的自动更新。** 变化只来自三个入口：用户点击项目的刷新按钮、Racco 自己的创建/删除、首次展示某个项目。终端里的 `git worktree add` / `remove` 不会自己出现，需要点一下刷新。

**派生结果为空必须是错误，不能当作"这个项目没有 Worktree"。** Git 对任何仓库都至少列出它自己的检出（非 Git 目录直接以 `fatal: not a git repository` 退出），所以零行在结构上不可能，只可能是读取失败。把它当成有效结果，会让一次读取失败把该项目全部会话变成孤儿。同理，"Git 回答了否"与"我们问不到"必须区分：前者是正常结果，后者降级为带说明的目录并保留上一次成功的列表。

两条不变量支撑整个设计：

1. **每个项目恰好有一个主 Worktree，其路径等于项目路径。** 它不是派生出来的行，而是项目自身：项目目录在 Git 眼里就是主工作区，非 Git 目录则没有 Git 语义。因此"导入一个目录后就能开会话"的既有行为不变。
2. **Racco 删除链接 Worktree 的目录是显式选择，绝不隐式删除。** 界面对链接 Worktree 提供删除：先确认，默认交由 Git 非强制删除；若目录 dirty 再二次确认后强制删除，磁盘目录真的消失，分支保留。目录已消失的条目只清理 Git 元数据，无需在缺失目录中检查 dirty。删除项目时默认**只解除注册**（项目条目 + 会话从 Racco 移除），链接 Worktree 目录原封不动地留在磁盘上——因为列表派生自 `git worktree list`，重新导入同一项目目录即可全部找回；只有用户显式勾选"同时删除磁盘上的 Worktree 目录"才执行级联删除，且级联不强制移除持有未结束轮次或正在压缩的目录（保留并报告为 skipped）。主 Worktree 没有删除入口——它的删除请求等价于删除项目，只解除注册、不触碰磁盘。这一条由 Racco 自己的路由保证（删除路径先按 `kind === "linked"` 匹配，项目路径不可能命中）；Git 拒绝删除主工作区（`--force` 也不生效）是第二道防线，用于兜住把项目路径直接传给删除接口的情况。新增 Worktree 种类时，这条路由必须一并考虑，不要让它落到 `worktree remove` 上。

**以 Worktree 为根的读取端点只接受已注册项目持有的目录。** 文件树/文件读取、模型目录、原生会话列表的 `path` 必须是某个已注册项目的项目路径（其主 Worktree）或该项目 catalog 中的派生 Worktree；任意存在的宿主目录都不算可读根。项目导入是用户显式向 daemon 开放其文件系统的动作，这些读取端点不把这份开放扩展到未注册路径。目录浏览器（`/api/directories`）仍按显式导航读取任意目录，那是导入项目自己的入口。

一项对未来改动有约束力的义务：Provider Driver 的目录参数保持按 `cwd` 传入。Worktree 只是给驱动换一个 `cwd` 取值，驱动本身不感知 Worktree 的存在；新增或修改驱动时不要把项目或 Worktree 概念带进驱动接口。

## Alternatives considered

**在 Racco 自己的 `worktrees` 表里登记 Worktree，`sessions.project_id` 换成外键。** 这是初稿，被否决：以 Racco 的登记为事实来源会隐藏用户在终端手工创建的 Worktree，与"看到所有 Worktree"的目标直接冲突。改为派生后，这张表连同它的外键一起消失——会话与 Worktree 的关联由 `sessions.cwd` 承担，`sessions.project_id` 保留为 `projects` 外键，语义精确化为"会话永远属于这个项目"。因此本次改动**不触碰持久格式、schema 版本不变、既有登记无需重新导入**，孤儿会话也自然可表达（`cwd` 匹配不到任何 Worktree 时归入项目的"已失效的 Worktree"分组）。

**不建任何持久状态，每次读列表都同步执行 `git worktree list`。** 结构上最干净，但左侧树、Dock、模型目录都会频繁读取，每个请求都 fork 一个 `git` 进程并解析输出，开销与延迟都不划算。选择按项目缓存合并并发读取；缓存不承担新鲜度，新鲜度由显式刷新决定。

**周期性轮询（含"廉价门禁 + 全量兜底"的两级扫描）。** 被否决，且否决的理由不是省 CPU——实测 `git worktree list --porcelain` 约 1.1 ms，十项目两秒一轮也只有约 0.055% 单核，两级门控省下的那点开销测不出来——而是周期性后台活动本身的代价：列表会在用户没动作时自己变，用户无法判断看到的是否最新，还可能在看某行准备删除时它凭空消失；终端里顺手建的临时 Worktree 会自己冒进侧栏；一个持续 fork 进程、持续广播消息的后台任务在无用户动作时运行，出问题时无法从界面判断它是否有关。改为手动刷新。

**用 `fs.watch` 监听 `.git` 以即时发现外部改动。** 被否决：Git 并不总是更新可监听的目录时间戳——`worktree lock`、`unlock`、`move` 不改变 `.git` 与 `.git/worktrees` 的 mtime（仓库没有 linked Worktree 时 `.git/worktrees` 甚至不存在）；而覆盖 `add`/`remove` 又要同时监听两处，最终仍需周期性兜底。为一个漏事件的信号付出复杂度不划算。

**对齐 orca-ide 的做法：2 秒 `stat` 门控 + 30 秒全量重算 + 窗口回前台强制全量，另加 60 秒节流。** 它需要轮询是因为要发现**新仓库**（`readdir` 遍历 workspace 根目录，成本随目录数增长），而 Racco 只需按项目问一次 `worktree list`，成本与 Worktree 数量无关。照搬会把上面那份代价一并买回来，换不到它解决的问题。

**在列表读取时自动执行 `git worktree prune` 清理元数据残留。** 被否决：Git 无法区分"目录被删除"与"目录暂时不可达"（未挂载的外接盘、休眠的加密卷），自动 prune 会抹掉后者的元数据，而元数据承载着分支占用关系。改为只展示 `prunable` 状态，不提供自动化清理。

**脏 Worktree 先移入回收目录再 `prune`（对齐 orca-ide 的 trash 目录）。** 可恢复性更好，但引入第二个生命周期概念和一处 Racco 无法校验其内容的持久存储；二次确认已经把是否丢弃的决定交给了用户。

**Worktree 根目录放在检出之外（如 `~/.local/share/racco-worktrees`）。** 初稿如此建议，被否决：采用与 daemon 其他持久状态同处的检内路径。代价记入 Consequences。

## Consequences

用户可以在同一项目下并行多条工作线：每个 Worktree 独立的工作目录与分支，各自的会话、文件浏览与模型目录互不干扰，Racco 里能看到终端手工建的 Worktree，也能就地创建和删除。

**Worktree 落在 Racco 源码检出内。** `~/.local/share/racco` 是安装脚本指向检出的符号链接，因此默认落点位于一个 Git 工作区内：在检出内执行 `git clean -xdf` 会连带删除它们，检出也会因这些目录长期显示为 dirty（`doctor` 报告 `dirty: true`）。前者靠约定规避——检出内的清理只用 `-df`；后者用检出根 `.gitignore` 锚定的 `/worktrees/` 条目缓解（锚定到根，避免误伤源码模块 `src/server/worktrees/`）。配置 `worktreeRoot` 到检出之外可同时消除两项，但只对 Racco 之后创建的有效。

**重新安装会改指符号链接。** 安装脚本按执行时的工作目录建立链接，重新安装到另一个检出会让 Racco 的创建位置随之漂移。已创建的 Worktree 按路径派生，不受影响。

**列表不会自动反映外部改动，一次派生失败也不会自行恢复。** 在 Racco 之外删除或 `git worktree move` 一个 Worktree 后，那行及其会话会一直显示到用户点刷新为止，点开会失败。这是有意接受的成本；缓解放在错误路径上（打开 `cwd` 已不存在的会话时提示该目录可能已被移除并可刷新列表），而不是恢复任何形式的轮询。因此失败时保留上一次完整的列表，在项目行显示降级原因，直到用户显式刷新成功；刷新不能丢掉可供回退的列表。

**Racco 的删除不限于自己创建的目录。** 因为列表包含手工创建的 Worktree，删除入口对它们同样开放（否则用户无法在 Racco 里清理自己建的东西）。实际保护来自 Git 的 `is a main working tree` 拒绝与前置的二次确认，而不是"只删自己的"这条不变量——这条保护不再是结构性的。

**Racco 新增对 `git` 可执行文件的运行依赖。** 只在创建、删除和列表派生时需要，但它从"可选工具"变成了需要探测并在缺失时给出可读错误的运行前提（`doctor` 已一并检查）。

**删除与会话操作必须互斥。** Worktree 的创建与删除按项目串行；会话创建、导入、原生删除、轮次启动与压缩在异步操作前占用目标目录，删除先取得互斥占用再检查运行状态。冲突请求立即拒绝，失败后释放占用，避免排队请求在用户未察觉时执行破坏性操作。项目删除覆盖所有所属目录。已运行或正在压缩的 Worktree 拒绝单独删除，项目级清理保留其目录；其余会话随目录一并移除登记并广播。

**磁盘删除已改为显式选择。** [删除动作的磁盘清理改为显式选择](../feature/2026-09-21-delete-explicit-disk-cleanup.md) 部分取代本记录不变量 2：删除项目默认不删 Worktree 目录（重新导入可找回），删除单个 dirty Worktree 需要两步确认。
