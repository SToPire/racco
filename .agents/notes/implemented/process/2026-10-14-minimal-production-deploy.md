# Agent Note: 显式停机发布生产构建

Status: implemented

## Problem

运行中的 daemon 已载入旧后端代码，静态资源却从构建目录读取。服务运行时直接替换生产产物，会短暂组合旧后端与新前端，导致接口或协议不一致。

## Decision

使用显式 `npm run deploy` 更新 systemd 用户服务：先在临时目录完成完整生产构建与源码一致性检查，再停止 `raccod.service`，删除旧产物并发布新产物，最后启动服务。停止失败不得替换产物，发布失败不得启动服务；编译失败不操作服务。生产构建锁覆盖整个操作，验证与预览构建不部署。

`npm run build` 只生成生产产物，不控制服务；运行当前产物的服务必须通过 deploy 更新，不能使用 build 后 restart 的顺序。部署命令由操作者在已安装的服务检出中显式执行，不自动识别安装目录或运行实例。不备份、不回滚、不重启旧实例，也不轮询构建标识；启动命令成功不代表应用已就绪。停机后的失败直接报错，由操作者修复产物或启动问题后手动恢复。

## Alternatives considered

**构建后直接重启：** 命令更短，但发布到重启之间仍可能由旧后端提供新静态资源，不能保证更新顺序。

**构建命令自动管理服务并备份恢复：** 可自动恢复失败部署，但需要实例识别、产物备份、恢复和就绪校验。当前接受人工处理失败，用显式部署命令和最小顺序约束解决代际混用。

## Consequences

编译期间服务继续运行，停机窗口只包含产物替换和启动；停止服务会中断连接及运行中任务，旧页面在更新后可能需要刷新，旧 hash 资源不保留。删除旧产物后若发布失败，服务保持停止且旧构建无法恢复；普通产物发布也不再保留临时回滚副本。这是接受的运维取舍，不增加自动恢复机制。发布顺序由[构建脚本测试](../../../../scripts/build.test.mjs)使用替代 systemctl 验证，不操作真实用户服务。

本记录持有构建与部署职责的边界，同范围没有需要完整替代或归档的现行记录；[内核实例锁](../bug-fix/2026-10-02-kernel-state-instance-lock.md)及[临时聊天图片](../feature/2026-09-27-ephemeral-chat-images.md)继续约束服务停止和启动时的资源生命周期。
