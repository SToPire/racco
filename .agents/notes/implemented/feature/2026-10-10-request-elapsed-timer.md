# Agent Note: 当前请求等待耗时

Status: implemented

## Problem

会话状态和停止按钮本身只能说明任务正在运行，不能说明用户已经等待多久。首段输出前的安静等待尤其容易被理解为请求没有发出；收到文字后，工具执行和后续生成仍可能持续。计时需要在切换视图、刷新及远程客户端重连后表达同一个当前请求，不能从组件重新挂载时开始计算。

## Decision

当前主 Agent 请求显示持续更新的“请求已用时”，覆盖从 Racco 接受执行到整轮任务结束的时间。计时起点是 daemon 完成校验、建立 `activeTurn` 并准备调用 Provider 的时刻，不等待 Provider 返回首段文字或推理摘要。此前保留发送按钮和输入区的提交忙碌反馈；校验、图片准备和新会话分配阶段不宣称已开始模型执行。本指标包括 Provider 启动、生成、工具调用和等待用户回答，界面不将其命名为“模型推理耗时”，也不推断底层单次模型调用的边界。

在 [SessionView](../../../../src/web/components/SessionView.tsx) 的公共输入区上方，将计时文本和现有停止按钮放在同一行，例如 `请求已用时 00:12  [停止生成]`。Chat、Trajectory 和查看子 Agent 时都显示同一个主请求的计时；查看子 Agent 时加上 `Main Agent` 归属提示。窄屏允许该行换行，停止入口始终可见。计时不插入消息时间线，不触发自动滚动，不在标题栏和每条消息中重复显示。

| 场景 | 展示与计时行为 |
|---|---|
| 提交尚未被 daemon 接受执行 | 保留提交忙碌反馈；没有活动请求时不显示执行计时。 |
| 当前请求开始 | 显示 `请求已用时 00:00`；即使尚无 Provider 输出也开始递增。 |
| 文字流式输出、工具执行或轮内自动压缩 | 继续计时，不因首次输出、工具切换或中间回复重置。 |
| `waiting_interaction` | 显示 `等待你回答 · 请求已用时 01:08`，继续计算总时长；回答后沿用同一起点。 |
| 用户点击停止 | 继续计时，直到 daemon 确认任务结束；点击本身不是终态。 |
| 正常完成、失败或中断 | 随活动请求清除一起收起计时；沿用已有结果、错误和中断反馈。下一条请求重新计时。 |
| WebSocket 断开或重新连接 | 停止本地外推，显示 `连接中断 · 最后确认用时 01:08`；连接打开但尚无新样本时改为“正在同步”。该数字取最近服务端样本，收到新状态后恢复或收起。 |

时长向下取整到秒，使用 `mm:ss`，超过一小时显示 `h:mm:ss`；每秒刷新一次，用等宽数字减少跳动。计时使用独立的 `role="timer"`、`aria-live="off"`，状态变化与秒数更新分开，避免屏幕阅读器每秒播报。首版仅展示活动请求，结束后不新增历史耗时、首字延迟、预计剩余时间或耗时告警；手动压缩继续使用已有反馈。新会话首次请求采用相同起点，进入会话页时展示已过去的时间，不能因导航重新从零开始。主轮次结束后仍在运行的后台子任务不延长或重新启动该计时。

本决策补充[跨视图会话控制](2026-09-22-continuous-session-controls.md)，沿用[无逐轮执行记录](../simplification/2026-09-17-session-state-without-turn-ledger.md)、[压缩忙碌反馈](2026-09-17-compaction-busy-feedback.md)、[会话显示缓存](../bug-fix/2026-09-22-session-switching.md)及[后台子任务独立寿命](../bug-fix/2026-09-22-codex-background-child-events.md)的边界。这些记录继续持有各自决策，没有被替代或需要移动的记录。

## 运行时契约

计时由 [SessionHub](../../../../src/server/session-hub.ts) 的当前 `activeTurn` 持有：增加每次执行唯一的 `id` 和服务端单调时钟起点，创建时开始、最终清理时删除。Codex 与 Claude 共用这一层，不分别从 Provider 文本、工具事件或原生 turn 标识猜测开始时间；也不使用会随内容更新的 `SessionSummary.updatedAt`。

[SessionSummary](../../../../src/shared/protocol.ts) 的必填字段 `activeRequest: { id: string; elapsedMs: number } | null` 提供当前请求计时。`elapsedMs` 是非负整数，表示服务端生成该份响应时距起点的毫秒数；没有当前主请求时为 `null`。会话列表、导入已有会话的响应、`session.upserted` 和 `session.snapshot` 在输出时使用同一投影即时计算，不能把旧样本留在 summary 中反复发送。终态与 `activeRequest: null` 在同一更新中发出，沿用现有“先清除活动任务再发布终态”的顺序。协议的全部生产端、消费端和 fixture 使用当前契约，不保留缺失字段的旧格式分支。

浏览器在接收样本时保存 `{id, elapsedMs, receivedAtMonotonic}`，显示值为 `elapsedMs + 本地单调时钟距接收时刻的差值`。同一请求的新样本用于校准，连接正常时不让可见秒数倒退；不同 `id` 必须重置，`null` 必须清理。服务端和客户端不比较各自的墙上时钟，避免远程设备时差及校时导致跳变。断线后仅展示最后收到的 `elapsedMs`，不将本地外推值冒充服务端仍在执行的证据。

样本及接收锚点按会话保存在浏览器显示状态中；切换视图和组件重挂载不得重新设置接收时刻。计时刷新只更新独立的小组件，可见会话每秒刷新，隐藏会话和后台页面停掉刷新任务；重新可见时按时间差立即重算并按现有流程同步会话。禁止通过每秒增加计数累计时长，也不让整个消息列表每秒重渲染。daemon 仅在原有状态更新和请求快照时附带计时样本，不新增每秒广播或轮询。

连接中断使缓存样本失去实时性，连接重新打开本身不能恢复计时外推。HTTP 会话列表读取期间收到的更新、删除和快照优先于该次列表响应；跨断线的旧列表响应不能更新会话状态，防止迟到响应复活已经结束的请求或覆盖新请求。

数据只存在于当前 daemon 内存及浏览器显示缓存，不改数据库、不增加逐轮账本或浏览器持久存储。刷新、切换会话和其他客户端打开时从当前快照恢复；daemon 重启沿用原有中断处理，清空计时且不重放请求。已完成的导入历史没有本功能的计时数据，不从历史消息补造。

## Alternatives considered

**只在前端看到 `running` 时创建秒表：** 改动少，但重挂载、刷新和其他客户端会有不同起点，且当前 `sending` 也被压缩操作复用，不能直接作为普通请求计时依据。

**只记录开始时间戳并用浏览器 `Date.now()` 相减：** 字段简单，但远程客户端与 daemon 的系统时间不一定一致。传输服务端已用时样本并在本地用单调时钟外推，避免把设备时差变成等待时长。

**在第一段输出出现时停止，或等待用户回答时暂停：** 分别衡量首响应延迟和排除用户等待的执行时间，都无法直接回答“当前请求已经过去多久”。首版保留一个总时长，用状态文案解释当前在等待谁。

**保存每轮耗时或增加服务端秒级广播：** 前者扩展为持久历史功能，后者增加无必要的网络与状态更新；当前请求的内存起点和客户端本地刷新足以支持此需求。

## Consequences

首段输出前及持续执行期间都有可读的等待时长，桌面和窄屏共用一个操作区，阅读导航不改变请求起点。[会话生命周期测试](../../../../src/server/session-hub.test.ts)约束首条与后续请求、等待回答、结束清理和重启边界；[计时浏览器测试](../../../../test/e2e/request-timer.spec.ts)覆盖跨视图、刷新、多客户端、后台恢复、断线和迟到列表响应。

服务端受理执行以前的浏览器传输、校验及新会话分配时间不计入该指标，因此提交阶段必须保留即时反馈；若后续明确需要“自点击发送起”的端到端时长，应单独定义其身份和跨客户端语义。已用时样本存在传输延迟，显示用于秒级等待反馈，不承诺精确性能测量。等待用户回答也计入总时长，文案必须避免让用户误认为模型仍持续推理。断线切换为最近服务端样本时数字可能回退，因此须同时改为“最后确认用时”，不能悄悄继续显示运行态。
