# Agent Note: 删除动作的磁盘清理改为显式选择

Status: implemented

## Problem

删除项目时 Racco 无条件级联删除所有链接 Worktree 的磁盘目录，删除单个 Worktree 时也会把未提交的修改和未跟踪文件一并丢弃。用户只是想移除 Racco 里的项目条目时，可能意外丢失磁盘上未提交的工作；删除项目与删除 Worktree 的破坏性在确认文案上不够醒目。

## Decision

磁盘删除从"隐式级联"改为"显式选择"。

**删除项目**的确认框提供复选框"同时删除磁盘上的 Worktree 目录"，默认不勾选。不勾选时只移除 Racco 的项目条目与会话，链接 Worktree 目录原封不动地留在磁盘上；因为 Worktree 列表派生自 `git worktree list`，重新导入同一项目目录即可全部找回。勾选时才执行 `git worktree remove --force` 级联删除（含丢弃未提交内容）；持有未结束轮次或正在压缩的链接 Worktree 的目录会被保留（报告中标记为 skipped），不在其下方强制移除，但它们的会话记录仍随项目删除一并销毁。项目目录本身两种情况下都不删除。

**删除单个 Worktree**改为两步确认：第一次确认删除（说明分支保留、目录会被删除）；dirty 判定放在服务器删除时，显式包含未跟踪文件，不受 Git 隐藏未跟踪文件的显示配置影响，也不信任客户端列表里可能过期的 dirty 标志——若目录 dirty 返回 409，客户端重新弹第二次确认（明示未提交的修改与未跟踪文件将一并丢弃、无法恢复）并以 `force=true` 重试。未确认强制删除时，实际 Git 删除也不传强制选项，防止检查后新增的工作被丢弃；只有二次确认后才允许强制删除。目录已经消失时，直接清理它的 Git 元数据。

删除在异步检查前取得目标目录的互斥占用，期间拒绝新的会话创建、导入、发送和压缩；进行中的会话初始化也会阻止删除。项目删除覆盖全部所属目录。这样删除前的运行状态检查不会被随后启动的操作绕过；冲突请求需要用户重试，失败后不会遗留占用。

## Alternatives considered

**删除 Worktree 也用复选框控制是否删磁盘：** 不符合派生模型——Worktree 列表来自 Git 实时派生，目录留着列表就在，"只从 Racco 元数据删除"这个动作没有可表达的状态，只会造成无法理解的行为（目录在但列表没有）。

**dirty 的 Worktree 默认拒绝删除，需勾选"强制删除"才放行：** 更保守，但比"两步确认"多一个界面状态，且用户明确偏好用确认框而非复选框表达"我了解后果"。两步确认同样把决定权交给用户，交互更轻。

**不勾选时把项目标记为"禁用"而非删除：** 引入第二个生命周期概念，与"删除即解除注册"的既有语义冲突，且重新导入已能完整找回，无需保留禁用态。

## Consequences

用户可以在 Racco 里放心删除项目条目而不触碰磁盘；误删项目后，重新导入原目录即可恢复全部 Worktree 及其分支。删除项目确认框现在是一个带复选框的自定义 `<dialog>`（原 `window.confirm` 无法容纳复选框），删除 Worktree 仍用浏览器确认框。删除 Worktree 时未提交内容仍可能被丢弃，但必须经过两步显式确认。

删除会话记录不代表执行收尾已经完成。关闭状态库前仍须等待已移除会话的取消收尾，避免迟到回调访问已关闭的状态。

与 [Worktree 管理](../architecture/2026-09-20-git-worktree-management.md) 的不变量 2 部分取代：该不变量由"Racco 删除链接 Worktree 的目录，但绝不删除项目目录"改为"Racco 删除链接 Worktree 的目录是显式选择，绝不隐式删除"。
