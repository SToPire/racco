# Agent Note: 移动端信息密度与键盘视口适配

Status: implemented

## Problem

手机上的固定外壳布局（100dvh、对话内部滚动）让 pinch 缩放只能等比放大整个界面，无法借此提高单屏信息量；默认根字号下的行距与间距在窄屏偏松，底部输入区（输入框、工具行、上下文行，待处理交互最高占 32dvh）占屏过高，新建对话页的空输入框固定约四行高度。Android 默认的键盘覆盖行为在键盘弹出后进一步压缩可视对话区，刘海屏底部横条也可能遮挡输入区。

## Decision

移动端（≤760px）媒体查询把根字号降为 15px，所有 rem 字号档位随之等比缩小一档，px 间距与控件尺寸不变；文本输入控件以 `!important` 固定为 16px，避免 iOS 对小于 16px 的聚焦输入强制放大页面——裸元素选择器会被 `.new-session-composer textarea` 等组件级类规则覆盖，守卫必须强制取胜。消息行距由 1.65 降为 1.5，时间线间距与顶部留白收紧，底部留白保留为浮动轮次导航的跑道。输入框内边距与行间距收紧，待处理交互卡高度上限降为 24dvh/240px，新建对话页输入框高度固定为 84px。viewport 增加 viewport-fit=cover 与 interactive-widget=resizes-content：后者使支持的浏览器（Android Chrome）在键盘弹出时压缩布局视口、输入框贴键盘上沿，不识别该指令的浏览器行为不变；前者撤销 Safari 的自动安全区留白，因此安全区补偿整体放在 `.app-layout` 外壳的四边 env() 内边距上，覆盖横竖屏与所有面板，固定定位的工具详情（≤1100px）逃逸外壳、单独补偿。保持不禁用 pinch 缩放，不引入 maximum-scale 或 user-scalable=no。

本决策在移动端细化[呈现一致性](2026-09-29-web-ui-presentation.md)的字号档位取舍：档位结构与桌面端取值不变，移动端整体降一档，原 11px 元信息下限在移动端约为 10.3px。[首页输入](../simplification/2026-09-18-home-composer.md)的共用键盘处理与表单职责不变，仅收窄空输入框的默认高度。没有记录被完整替代。

## Alternatives considered

**移动端改为文档流滚动（对话区不再内部滚动）：** pinch 缩放与平移可获得普通网页体验，但需要重写跟随滚动与轮次导航对滚动容器的耦合，并重新引入 iOS 固定底栏与键盘的兼容问题；用户诉求是缩小界面而非放大查看，密度调整已覆盖该诉求。

**逐组件分别下调字号：** 控制更细，但全部字号共用一套 rem 档位，整体缩放根字号一处生效且避免各组件再次漂移。

## Consequences

单屏可见对话行数增加，输入区高度下降，Android 键盘弹出后对话区自动让位；刘海与 Home 指示条区域在横竖屏都不再遮挡外壳内的面板与输入区，但固定浮层（工具详情、选择菜单等）需要各自留意安全区。代价是移动端最小元信息文字约 10.3px，接近中文可读性下限，后续继续下调需重新评估；文本输入一律 16px，大于周围缩小后的文字。桌面端（>760px）不受影响。[浏览器回归](../../../../test/e2e/web-presentation.spec.ts)继续覆盖窄屏内容边界与消息对齐，[活动可读性](../../../../test/e2e/chat-activity.spec.ts)对移动端按视口放宽分数行高取整带来的 1px 高度差。
